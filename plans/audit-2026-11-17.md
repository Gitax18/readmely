**Scope:** everything on `main` after Phase 0 Steps 1–2: product description, plans, the diagram guide, `Makefile`, Docker Compose, Dockerfile, and the Go service (`services/core`).
**Method:** file-by-file read, plus the test, lint and container results from Step 2.

**Verdict:** no critical issues. The code is in good shape for this stage. Most findings are mismatches between documents, and a few small hardening gaps that are cheap to close now.

Each finding gets one of three decisions:
- **Fix now:** small, and cheaper today than later.
- **Fix in phase N:** real, but belongs to work that hasn't started.
- **Ignore:** accepted on purpose, with the reason.

## Fix now

| ID | Severity | Where | Problem | Fix |
|---|---|---|---|---|
| A1 | High | `server.go`, compose | **`/readyz` will be public in production.** Anyone on the internet could see which dependency is down, and every call makes a database round trip, so it can be used to load the database. | Keep `/healthz` public. Serve `/readyz` on a separate internal-only port (or require an internal token). Apply the same rule in the Python service from the start. |
| A2 | Medium | `.env.example`, `Makefile`, compose | **Passwords with `@ : / ? # %` silently break the connection URLs**, because they are inserted into `postgres://user:pass@...` without encoding. | A3 | Medium | `project-description.md` §4.1 | **Cost model is priced on Claude**, but decision D8 says the launch providers are OpenAI and xAI. The margins and break-even depend on these numbers. | Re-price §4.1 on OpenAI and xAI rates (checked on the providers' own pages), or record that the figures are a Claude-based proxy. |
| A4 | Medium | `project-description.md` §2.10 | **Sign-up method contradicts D4.** The description says "GitHub or email"; the decision is Google + GitHub + 2FA, with email still open. | Align the text with D4 and leave the email option to the Phase 2 auth discussion. |

## Ignore (accepted, with reason)

| ID | Item | Why it's acceptable |
|---|---|---|
| C1 | A readiness probe that ignores its context leaves one goroutine running until it returns. | Bounded by the client's own timeouts, documented in the code, and both real clients (pgx, go-redis) respect the context. |
| C2 | `server.Run` wraps `srv.Handler`, so it must be called once per server. | Documented. There is exactly one caller. |
| C3 | If a handler panics after it started writing, the generic 500 can't replace the partial response. | Unavoidable in HTTP. The panic is still logged with its request ID. |
| C4 | `freeAddr` in the API tests closes a port and reuses it, a theoretical race. | 15 consecutive clean runs. Only a test helper. |
| C5 | `make run-api` sources `.env` as shell code. | `.env` is the developer's own git-ignored file. Same trust level as the shell itself. |
| C6 | `.env.example` contains the placeholder `change-me-local-only`, which works if not changed. | Local only, every port is bound to `127.0.0.1`, and production never reads `.env`. |
| C7 | The diagram guide mentions "Conveyor", a personal example project. | Harmless context in a design note. |

## What is in good shape

- **Security baseline:** no secrets in git, data stores bound to localhost, mandatory credentials, non-root read-only containers with all capabilities dropped, errors never echo configuration values, client request IDs validated, query strings kept out of logs.
- **Tests:** 57 passing with the race detector; coverage of 95–100% in every core package; resilience checked in real containers; two real bugs found and fixed by repeated runs.
- **Process:** every step planned and approved before code, typed commits, decisions recorded with their reasons.

## Effect on Step 3 (Python service)

The revised Step 3 plan in [phase-0-foundations.md](phase-0-foundations.md) applies A1, A2 and B4 from day one: readiness on an internal-only route, URL-safe credentials, and response shapes identical to the Go service.
